# Abstract storage interface: local filesystem in dev, cloud object storage in prod

Image storage is behind a thin storage interface (`upload(file) → url`, `read(url) → stream`) with two implementations: a local-filesystem implementation used in the Docker dev environment (zero external dependencies, volume-mounted), and an S3-compatible implementation for production. We chose this over local-only (which doesn't scale across instances or serve a CDN in prod) and over cloud-only (which forces cloud credentials and a MinIO emulator into the dev environment). The trade-off is maintaining two implementations, but the interface is tiny and the local impl is trivial — far cheaper than migrating stored images and rewriting upload code later.

**As built.** The interface grew two methods and the drivers own the URL shape. `delete(url)` was added so a Photo upload that fails to persist is not left behind as an orphan file (issue 11's photo replacement needs the same operation). `urlFor(key) → url` was added so the HTTP layer never has to know a driver's URL convention: the serving route receives a bare key and asks the driver for the url to read. The local driver returns a root-relative url (`/uploads/<key>`); the S3 driver returns an **absolute public/CDN url**, so in production the client fetches Photos straight from the bucket or a CDN and the API does not proxy image bytes — the reason this ADR exists. The driver is selected by config (`STORAGE_DRIVER`); an unsupported or unconfigured driver refuses to boot rather than failing an upload at runtime, so a misconfigured deployment is caught at startup instead of at the first Photo.
