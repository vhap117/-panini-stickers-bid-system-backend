# Development-only login seam for the Web front-end

The Web front-end must be able to develop against the real API without a social-login round trip, so the backend exposes `POST /auth/login/dev` when, and only when, `DEV_AUTH_ENABLED` is `true` or `1`. This is not social login on the Web: no Google (or other provider) flow is added or changed, and the seam lives only in the development environment. The endpoint is fail-closed — off by default, absent from the router when disabled (a request gets the normal 404, not an auth failure), and refused outright in production by both `configFromEnv` and the boot guard, which throw if dev auth is enabled while `NODE_ENV=production`. The route issues a session through the same identity resolver and session machinery as every other provider (ADR-0003, ADR-0011), so the resulting access token is a real Bearer JWT that works on every protected REST route and Socket.IO connection exactly like a Google-issued one. It offers three fixed personas (`dev`, `alice`, `bob`), each mapped to a stable provider id so repeat logins, including across process restarts, resolve to the same User; an unknown persona is rejected with the locale-neutral `INVALID_DEV_PERSONA` code (ADR-0014). Dev identities are stored with `email = null`, so ADR-0003's email auto-link can never attach a dev identity to a real User and no Google token can ever reach a dev User. Trade-offs: a development credential ships in the codebase, mitigated by the fail-closed default and production refusal rather than by secrecy; and deterministic personas accumulate state in whichever database they are used against, so resetting dev data means truncating the users table.
